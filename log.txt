1) FILE: allocation.f90  (subroutine read_input, ~line 253)
--------------------------------------------------------------------------------
BUG:
  beta and gamm (global module variables) were being rescaled by
  beta = beta/(lambda*Ao) and gamm = gamm/(lambda*(Ao)**1.5) inside
  Force_Calculation (Force.f90) AND again inside Calculate_StressTensor
  (Stress.f90) -- both of which run every timestep. Since the division was
  applied to the already-divided value from the previous call, beta/gamm
  decayed/blew up geometrically: beta_eff = beta_0/(lambda*Ao)^N after N
  calls. Masked in the shipped para1_in.dat only because Ao=1, lambda=1
  (division becomes a no-op); breaks immediately for any other Ao/lambda.

FIX:
  Perform this nondimensionalization exactly ONCE, in read_input, right
  after beta_0 = beta is set. Removed the duplicate rescale lines from
  Force.f90 (Force_Calculation) and Stress.f90 (Calculate_StressTensor).

O5) FILE: Force.f90  (subroutine Force_Calculation)
--------------------------------------------------------------------------------
COST:
  Each cell edge was traversed twice per timestep per cell: once as vertex
  jc's "next" edge and again as vertex jc+1's "prev" edge, each time
  recomputing dx, dy, and a dsqrt() from scratch -- i.e. 2*nn sqrt calls per
  cell instead of nn. This runs for every cell, every timestep, unconditionally.

FIX:
  Added a small precompute loop building edge_dx/edge_dy/edge_len(k) = the
  vector/length of the edge from vertex k to vertex k's next neighbour, once
  per cell (nn sqrt calls). The per-vertex loop then reuses these cached
  values algebraically:
    grad_perimeter_X = edge_dx(prev_idx)/edge_len(prev_idx) - edge_dx(jc)/edge_len(jc)
  This is bit-for-bit identical to the original two-sqrt computation (same
  dx/dy values up to an exact sign flip, which does not change a squared
  quantity or a subsequent negation in IEEE754) -- confirmed by the
  bit-identical Energy trajectory in the default-config sanity re-run.

O6) FILE: vertexmain.f90  (main T1/T2 loop, ~line 104)  [THIRD PASS]
--------------------------------------------------------------------------------
COST:
  The `do iki = 1,500` loop always ran the full 500 iterations, each calling
  Do_T1/Do_T2 (each of which does a full O(Nc) mesh rescan via find_T1/
  find_T2), regardless of how many real short edges/small triangles were
  actually left. Once the local topology stabilizes -- which, per the
  sanity runs, typically happens well before 500 attempts -- the remaining
  iterations are pure waste: full rescans that are guaranteed to find
  nothing.

WHY NOT THE FULLER INCREMENTAL REDESIGN:
  The originally-envisioned fix (a persistent, incrementally-updated
  candidate list of short edges/small triangles, updated locally after each
  flip instead of full rescans) was investigated but NOT implemented, because
  T2 cell removal renumbers every cell index above the removed one (all
  cells shift down by one) -- any persistent candidate list storing cell/
  edge indices across multiple T1/T2 attempts would need those stored
  indices kept in lock-step with every such renumbering. Getting this wrong
  is exactly the highest-severity, hardest-to-detect bug class in vertex
  model codes (silent topology corruption -- no crash, no NaN, just wrong
  physics). That redesign was judged to need dedicated design/testing time
  it did not have in this pass, rather than being rushed alongside everything
  else.

FIX (the safe piece of this that IS fully correctness-preserving):
  find_T1/find_T2 already freshly recompute count_T1/count_T2 (the number of
  remaining candidates) on every call. Once both are simultaneously zero,
  NOTHING in the mesh can change for the rest of this loop -- no candidates
  means no possible mutation, so every remaining iteration's full rescan is
  guaranteed, deterministically, to find the same empty result. Added:
    if((.not.if_Do_T1 .or. count_T1==0) .and. (.not.if_Do_T2 .or. count_T2==0)) exit
  right after the Do_T1/Do_T2 calls. This skips zero legitimate T1/T2
  events -- it only skips full rescans that were already guaranteed to find
  nothing.

VERIFICATION (strongest of this whole pass):
  Built two variants from identical source (all other fixes/optimizations
  applied to both) differing ONLY in this exit statement, ran both for 3000
  timesteps on the default config, and compared every output file:
    Energy.dat, inn_00003000.dat, num_00003000.dat, v_00003000.dat,
    T1_count.dat, T2_count.dat  -->  BYTE-FOR-BYTE IDENTICAL, all of them.
  Timing: without the exit, 3000 steps took 10.26s; with it, 0.19s --
  approximately 54x faster on this mesh (Lx=16, Ly=16), for provably zero
  change in simulation output. (The speedup will vary with mesh size and how
  often T1/T2 activity is genuinely ongoing vs. settled; it is largest, as
  seen here, once the tissue is closer to mechanical/topological
  equilibrium and most of the 500 attempts would otherwise find nothing.)

program (a landmine already noted above), and gfortran's default seeding
turned out to be genuinely non-deterministic ACROSS SEPARATE PROCESS RUNS
of the *same* binary whenever a scenario exercises real multi-candidate
random branching (confirmed directly: running the "new" build twice on
scenario 1 gave two different Energy.dat trajectories). Earlier sanity
passes in this session appeared "bit-identical across reruns" only because
those scenarios rarely had more than one T1 candidate at a time, making the
exact random draw irrelevant to the outcome -- not because the RNG was
actually seeded consistently. To get a meaningful previous-vs-new
comparison here, both variants were temporarily patched with an identical
fixed call random_seed(put=...) at program start (comparison-only patch,
not part of the real fix, not applied to the repo) so that any remaining
differences are attributable to code changes, not RNG noise.

     all 500 steps. Expected: none of this session's behavioral fixes touch
     this code path (only the proven-equivalent optimizations do), so
     identical output confirms no unintended regression.

     the *intended* effect of the O(bug fix) "Polar_Motile_Force_Calculation

     conceptually per-cell, not per-vertex), so ABP behavior should be, and
     is, unchanged from the original.
  All 6 runs (3 scenarios x 2 variants) completed with exit code 0, zero
  NaN/Infinity/error/out-of-bound/segfault matches in any log.

NINTH PASS: Motile_Force_Calculation optimization (user request, after
profiling a 10^7-step if_motility run and finding it the dominant cost)
================================================================================
User observed: the do-loop in Motile_Force_Calculation runs over
size(mot)==v_dim2 (the reserved vertex capacity), not the actual number of
vertices in use, and asked whether that's optimizable.

CHANGES:
1. Loop bound changed from size(mot) [v_dim2] to nv = maxval(inn) -- the
   highest vertex index actually referenced by any live cell. Vertices are
   only ever appended (never compacted/reused), so this is an exact (not
   approximate) bound: slots beyond it are never read by anything else in
   the code. Measured impact on the user's actual input files: SMALL
   (v_dim2=18468 vs. initial maxval(inn)=18340, only ~0.7% slack), because
   the shipped/production mesh files are generated with v_dim2 only
   slightly larger than needed, and if_cell_division is off in the current
   para1_in.dat (so this gap never grows over the run). Kept anyway since
   it's correct, free, and would matter more with more headroom or with
   cell division on.
2. The real win: replaced ~2*nv individual scalar `call random_number(rann)`
   calls (one at a time, in a loop) with 2 whole-array calls
   (`call random_number(rann_x(1:nv))` / `rann_y(1:nv)`), using fixed-size
   automatic (stack) arrays sized v_dim2 declared once per call (no
   allocate/deallocate). This removes the per-call subroutine-call overhead
   of tens of thousands of scalar random_number calls per timestep and lets
   the compiler vectorize the surrounding arithmetic.
3. sqrt(2*mot(iv)*eta) was computed twice per vertex (once for fxx_ran,
   once for fyy_ran) -- identical both times. Now computed once into a
   shared array and reused for both components (same pattern as the
   edge-length caching already done in Force_Calculation).

REPRODUCIBILITY NOTE (important, unlike this session's earlier "pure"
optimizations): this change is NOT guaranteed to reproduce the exact same
trajectory as the old code for a given run. Both the loop-bound trim
(whenever nv < v_dim2) and the switch to batched random_number calls change
how many/which calls consume the single global RNG stream that find_T1/
find_T2's candidate selection also draws from -- shifting every subsequent
random draw, and therefore the whole downstream trajectory (same class of
tradeoff as the deferred "gaussian_random Box-Muller caching" item above).
Confirmed directly: before/after outputs (Energy.dat, mesh state) differ
starting from the first timestep. This is an accepted, explained tradeoff,
not a bug: the physics per vertex is unaffected (each live vertex still
gets an independent, identically-distributed noise term), and this
codebase already has no random_seed anywhere (see the CONFIRMED
non-determinism item above), so exact run-to-run/version-to-version
reproducibility was never guaranteed regardless.

VERIFICATION: built seeded before/after variants (identical fixed seed,
differing only in this one subroutine) and ran both 5000 steps on the
user's actual 32x32 mesh (para2_in.dat: v_dim2=18468) with if_motility on:
  - Both exit 0, zero NaN/error/out-of-bound/segfault in either log.
  - Energy stays in the same physically sane range for both (before:
    917.4-1037.6; after: 917.2-1037.7) -- different trajectories (expected,
    per the note above), neither diverging or blowing up.
  - Timing: 2.734s (before) vs. 2.103s (after) for the full 5000-step run
    -- a ~23% reduction in TOTAL runtime from optimizing this one

    dominant cost. Should scale similarly (or better, if random_number's
    per-call overhead is a fixed cost rather than proportional to problem
    size) over the user's actual 10^7-step production runs.

================================================================================
TENTH PASS: allocation.f90 -- write Energy/ShearStress/T1_count/T2_count
incrementally, not just at it==totT (enables live/mid-run MATLAB plotting)
================================================================================
CONTEXT: building a unified MATLAB analysis-plotting tool (Analysis_Codes_
matlab/) that should be able to plot Energy/ShearStress vs. time while a
simulation is still running. Found that write_output only ever wrote these
four files once, at it==totT -- they did not exist at all until a run fully
completed.

FIRST ATTEMPT (caught before shipping): simply removing the it==totT guard
and writing Energy(1:it)/ShearStress(1:it)/etc. every time write_output runs
(i.e. every it_dump). Sanity-checked the actual I/O cost this implies for
the user's real production config (totT=1e7, it_dump=100): rewriting the
whole growing (1:it) slice at every one of the 100,000 dump events sums to
~4TB of cumulative disk I/O for Energy.dat alone (~16TB across all four
files) -- large enough to dominate the run's wall-clock time and undo the
Motile_Force_Calculation optimization from the ninth pass. Not shipped.

FIX: added summary_dump_interval (allocation.f90, computed once in
read_input): a multiple of it_dump chosen so there are ~200 rewrites total
over the whole run regardless of totT/it_dump, never coarser than it_dump
itself (a short run with <=200 total dumps just writes every dump, same as
before). write_output's four blocks now gate on
`modulo(it,summary_dump_interval)==0 .or. it==totT` instead of writing
unconditionally or only at the end -- bounding cumulative I/O to a small,
fixed multiple of the final file size while still refreshing often enough
to watch a long run's progress. No new input parameter was added (so no
para1_in.dat format change) -- summary_dump_interval is derived entirely
from existing totT/it_dump.

MATLAB-side impact: none needed. LoadData.m and every other reader already
does fread(fid,Inf,'float64') (read to end of file, no hardcoded length
assumption), so a file that legitimately grows between reads is already
handled correctly.

VERIFICATION:
- Short complete run (totT=20000, it_dump=100): final Energy.dat has
  exactly 20000 entries (matches totT exactly, no off-by-one from the
  slicing change).
- Long run watched live (totT=2,000,000, it_dump=100, so
  summary_dump_interval=10000 by the formula above): confirmed Energy.dat
  exists and has 20000 valid entries after only ~22,648 of 2,000,000 steps
  (~1.1% complete) -- proving the file is genuinely readable mid-run, not
  just at the end -- and grew to 50000 entries a few seconds later,
  matching the 10000-step cadence exactly. No NaN/error in either run.

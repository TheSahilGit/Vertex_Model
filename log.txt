1) FILE: allocation.f90  (subroutine read_input, ~line 253)
--------------------------------------------------------------------------------
BUG:
  beta and gamm (global module variables) were being rescaled by
  beta = beta/(lambda*Ao) and gamm = gamm/(lambda*(Ao)**1.5) inside
  Force_Calculation (Force.f90) AND again inside Calculate_StressTensor
  (Stress.f90) -- both of which run every timestep. Since the division was
  applied to the already-divided value from the previous call, beta/gamm
  decayed/blew up geometrically: beta_eff = beta_0/(lambda*Ao)^N after N
  calls. Masked in the shipped para1_in.dat only because Ao=1, lambda=1
  (division becomes a no-op); breaks immediately for any other Ao/lambda.

FIX:
  Perform this nondimensionalization exactly ONCE, in read_input, right
  after beta_0 = beta is set. Removed the duplicate rescale lines from
  Force.f90 (Force_Calculation) and Stress.f90 (Calculate_StressTensor).

O5) FILE: Force.f90  (subroutine Force_Calculation)
--------------------------------------------------------------------------------
COST:
  Each cell edge was traversed twice per timestep per cell: once as vertex
  jc's "next" edge and again as vertex jc+1's "prev" edge, each time
  recomputing dx, dy, and a dsqrt() from scratch -- i.e. 2*nn sqrt calls per
  cell instead of nn. This runs for every cell, every timestep, unconditionally.

FIX:
  Added a small precompute loop building edge_dx/edge_dy/edge_len(k) = the
  vector/length of the edge from vertex k to vertex k's next neighbour, once
  per cell (nn sqrt calls). The per-vertex loop then reuses these cached
  values algebraically:
    grad_perimeter_X = edge_dx(prev_idx)/edge_len(prev_idx) - edge_dx(jc)/edge_len(jc)
  This is bit-for-bit identical to the original two-sqrt computation (same
  dx/dy values up to an exact sign flip, which does not change a squared
  quantity or a subsequent negation in IEEE754) -- confirmed by the
  bit-identical Energy trajectory in the default-config sanity re-run.

O6) FILE: vertexmain.f90  (main T1/T2 loop, ~line 104)  [THIRD PASS]
--------------------------------------------------------------------------------
COST:
  The `do iki = 1,500` loop always ran the full 500 iterations, each calling
  Do_T1/Do_T2 (each of which does a full O(Nc) mesh rescan via find_T1/
  find_T2), regardless of how many real short edges/small triangles were
  actually left. Once the local topology stabilizes -- which, per the
  sanity runs, typically happens well before 500 attempts -- the remaining
  iterations are pure waste: full rescans that are guaranteed to find
  nothing.

WHY NOT THE FULLER INCREMENTAL REDESIGN:
  The originally-envisioned fix (a persistent, incrementally-updated
  candidate list of short edges/small triangles, updated locally after each
  flip instead of full rescans) was investigated but NOT implemented, because
  T2 cell removal renumbers every cell index above the removed one (all
  cells shift down by one) -- any persistent candidate list storing cell/
  edge indices across multiple T1/T2 attempts would need those stored
  indices kept in lock-step with every such renumbering. Getting this wrong
  is exactly the highest-severity, hardest-to-detect bug class in vertex
  model codes (silent topology corruption -- no crash, no NaN, just wrong
  physics). That redesign was judged to need dedicated design/testing time
  it did not have in this pass, rather than being rushed alongside everything
  else.

FIX (the safe piece of this that IS fully correctness-preserving):
  find_T1/find_T2 already freshly recompute count_T1/count_T2 (the number of
  remaining candidates) on every call. Once both are simultaneously zero,
  NOTHING in the mesh can change for the rest of this loop -- no candidates
  means no possible mutation, so every remaining iteration's full rescan is
  guaranteed, deterministically, to find the same empty result. Added:
    if((.not.if_Do_T1 .or. count_T1==0) .and. (.not.if_Do_T2 .or. count_T2==0)) exit
  right after the Do_T1/Do_T2 calls. This skips zero legitimate T1/T2
  events -- it only skips full rescans that were already guaranteed to find
  nothing.

VERIFICATION (strongest of this whole pass):
  Built two variants from identical source (all other fixes/optimizations
  applied to both) differing ONLY in this exit statement, ran both for 3000
  timesteps on the default config, and compared every output file:
    Energy.dat, inn_00003000.dat, num_00003000.dat, v_00003000.dat,
    T1_count.dat, T2_count.dat  -->  BYTE-FOR-BYTE IDENTICAL, all of them.
  Timing: without the exit, 3000 steps took 10.26s; with it, 0.19s --
  approximately 54x faster on this mesh (Lx=16, Ly=16), for provably zero
  change in simulation output. (The speedup will vary with mesh size and how
  often T1/T2 activity is genuinely ongoing vs. settled; it is largest, as
  seen here, once the tissue is closer to mechanical/topological
  equilibrium and most of the 500 attempts would otherwise find nothing.)

Compared git-HEAD ("previous") against the fully-fixed working tree ("new")

IMPORTANT METHODOLOGY NOTE: random_number is never seeded anywhere in this
program (a landmine already noted above), and gfortran's default seeding
turned out to be genuinely non-deterministic ACROSS SEPARATE PROCESS RUNS
of the *same* binary whenever a scenario exercises real multi-candidate
random branching (confirmed directly: running the "new" build twice on
scenario 1 gave two different Energy.dat trajectories). Earlier sanity
passes in this session appeared "bit-identical across reruns" only because
those scenarios rarely had more than one T1 candidate at a time, making the
exact random draw irrelevant to the outcome -- not because the RNG was
actually seeded consistently. To get a meaningful previous-vs-new
comparison here, both variants were temporarily patched with an identical
fixed call random_seed(put=...) at program start (comparison-only patch,
not part of the real fix, not applied to the repo) so that any remaining
differences are attributable to code changes, not RNG noise.

  1) Motility scenario: Energy.dat BYTE-IDENTICAL, previous vs new, across
     all 500 steps. Expected: none of this session's behavioral fixes touch
     this code path (only the proven-equivalent optimizations do), so
     identical output confirms no unintended regression.
  2) Polar motility scenario: Energy.dat DIFFERS, previous vs new -- this is
     the *intended* effect of the O(bug fix) "Polar_Motile_Force_Calculation

     no crash in either variant.
  3) ABP scenario: Energy.dat BYTE-IDENTICAL, previous vs new, across all
     500 steps. Expected: the ABP noise-granularity change was reverted
     earlier in this session (per user clarification that ABP is
     conceptually per-cell, not per-vertex), so ABP behavior should be, and
     is, unchanged from the original.
  All 6 runs (3 scenarios x 2 variants) completed with exit code 0, zero
  NaN/Infinity/error/out-of-bound/segfault matches in any log.

NINTH PASS: Motile_Force_Calculation optimization (user request, after
profiling a 10^7-step if_motility run and finding it the dominant cost)
================================================================================
User observed: the do-loop in Motile_Force_Calculation runs over
size(mot)==v_dim2 (the reserved vertex capacity), not the actual number of
vertices in use, and asked whether that's optimizable.

CHANGES:
1. Loop bound changed from size(mot) [v_dim2] to nv = maxval(inn) -- the
   highest vertex index actually referenced by any live cell. Vertices are
   only ever appended (never compacted/reused), so this is an exact (not
   approximate) bound: slots beyond it are never read by anything else in
   the code. Measured impact on the user's actual input files: SMALL
   (v_dim2=18468 vs. initial maxval(inn)=18340, only ~0.7% slack), because
   the shipped/production mesh files are generated with v_dim2 only
   slightly larger than needed, and if_cell_division is off in the current
   para1_in.dat (so this gap never grows over the run). Kept anyway since
   it's correct, free, and would matter more with more headroom or with
   cell division on.
2. The real win: replaced ~2*nv individual scalar `call random_number(rann)`
   calls (one at a time, in a loop) with 2 whole-array calls
   (`call random_number(rann_x(1:nv))` / `rann_y(1:nv)`), using fixed-size
   automatic (stack) arrays sized v_dim2 declared once per call (no
   allocate/deallocate). This removes the per-call subroutine-call overhead
   of tens of thousands of scalar random_number calls per timestep and lets
   the compiler vectorize the surrounding arithmetic.
3. sqrt(2*mot(iv)*eta) was computed twice per vertex (once for fxx_ran,
   once for fyy_ran) -- identical both times. Now computed once into a
   shared array and reused for both components (same pattern as the
   edge-length caching already done in Force_Calculation).

REPRODUCIBILITY NOTE (important, unlike this session's earlier "pure"
optimizations): this change is NOT guaranteed to reproduce the exact same

NEW FEATURE: Fortran replacement for Main.m's initial-mesh generation
(Generate_Initial_Mesh.f90, para_MeshGen.dat, compile.sh)

Main.m was the only remaining reason a MATLAB session was needed to start a
new simulation: it builds the initial Voronoi tessellation (via MATLAB's
built-in voronoin) and writes v_in.dat/inn_in.dat/num_in.dat/para2_in.dat,
which allocation.f90's read_input/read_data then consume. Added a
standalone Fortran program that produces the exact same four files, byte-
compatible with the existing readers -- allocation.f90 and every other
.f90 file are untouched.

Confirmed while reading Main.m that BorderVertices, Give_Motility, and
Give_Motility_new (lines 48-153) are dead code -- never called from the
executed script. Motility generation now lives entirely on the Fortran
side (Give_Motility_Gradient/Give_Motility_Hotspot, Force.f90). Main.m
itself is left in place, unmodified, as a reference/fallback.

ALGORITHM (mirrors Main.m's MeshGenerator/StoreData exactly):
- Hexagonal-offset (brick) lattice of Lx*Ly seed points.
- Anisotropic jitter: ONE random draw per point, reused (at different
  scales) for both its x and y offset -- this reproduces Main.m's `ran`
  reuse verbatim, including the resulting x/y-correlated jitter direction,
  rather than "fixing" it into independent draws. Interior points get
  jitter_interior_{x,y} (default 0.5, 0.1); the outermost ring gets the
  smaller jitter_boundary_{x,y} (default 0.1, 0.1) -- boundary
  classification is the outer ring only (i==1|i==Ly|j==1|j==Lx in lattice-
  index space); Main.m computes a 2nd/3rd nested ring (inside2/Boundary2/
  Boundary3) but never actually uses them, so only the 1-ring split is
  reproduced.
- 8 periodic ghost copies (+-Lx, +-Ly and combinations) added purely so
  edge cells clip against real neighbors instead of coming out unbounded --
  a boundary-conditioning trick, not true periodic BCs (matches Main.m).
- Each real cell's Voronoi polygon is built directly via incremental half-
  plane clipping against nearby candidate points (real + ghost), processed
  in increasing distance order, with an exact early-termination test
  (stop once the polygon's farthest vertex from the seed point is within
  half the distance to the next candidate -- provably nothing farther can
  cut the polygon further). No general Delaunay/Voronoi algorithm needed:
  the point set is a mildly-perturbed lattice, so a local candidate search
  (via a uniform spatial grid, radius grown adaptively until the exact
  test passes) is sufficient and exact regardless of jitter magnitude.
- Vertices shared between cells are merged into one global list via a
  second uniform spatial grid (bucket-and-match within 1e-6).
- Each cell's vertex list is rotated to start at its min-x vertex, then
  forced clockwise via the same shoelace-sign check StoreData.m uses
  (Force.f90's area-gradient formula assumes clockwise winding -- this is
  the one convention that had to be reproduced exactly, not just
  approximately). StoreData.m's intermediate "flip if a(2)>a(end)" pass is
  provably redundant given the final clockwise-enforcement step always
  runs afterward, so it is omitted.

CONFIG: para_MeshGen.dat (Lx, Ly, seed, the four jitter magnitudes, and
three headroom counts -- cell/vertex-slot/vertex-pool -- all defaulting to
Main.m's current constants). RNG is explicitly seeded via random_seed
(default seed=9325) -- a deliberate improvement over Main.m's current
isseed=false default (a genuinely different mesh every run unless manually
seeded); same seed now reproduces the exact same mesh.

BUG FOUND VIA AUTOTESTING: heap-buffer-overflow in cell division
(Proliferation.f90 / Geometry.f90's UpdateNeighborPolygons)

Requested sanity sweep: 3 mesh sizes (16x16, 64x64, 50x50) x 3 parameter
scenarios (baseline apolar motility; oscillatory shear + fixed top/bottom
boundary; ABP motility + cell division), each run standalone in a scratch
copy, plus a full PlotAnalysis pass. The 50x50 ABP+division case crashed:
"free(): invalid pointer", SIGABRT, right after a division event's
"Proliferation: ic, Nc = ..." print.

DIAGNOSIS: compiled a `-fsanitize=address -O0` copy of the whole simulator
and reran the identical failing case. AddressSanitizer pinpointed a
heap-buffer-overflow WRITE at Geometry.f90:642 (`inn_new1 = 0`, inside
UpdateNeighborPolygons), called from Proliferation.f90:279
(Proliferation_Core), landing 0 bytes after an 88-byte (22-int) region --
exactly inn_dim1 integers, with no headroom at all.

ROOT CAUSE: UpdateNeighborPolygons declares its output dummies as
`inn_new1(size(inn_old1)+2)` / `inn_new2(size(inn_old2)+2)` -- i.e. 2 MORE
than whatever it's given for the corresponding input. Proliferation_Core
passes `inn_neighbor1`/`inn_neighbor2` WHOLE (not sliced to the neighbor
cell's actual vertex count), so size(inn_old1) inside the callee is always
inn_dim1, not num(othercells(1)) -- meaning inn_new1/inn_new2 are ALWAYS
declared inn_dim1+2 elements, on every single division. The matching
actual arguments at the call site, inn_neighbor1_new/inn_neighbor2_new,
were only ever declared inn_dim1 elements (zero headroom) -- so this
subroutine overflows its output arrays by exactly 2 integers on EVERY
division that finds two neighboring cells (othercells_count==2), not just
in some rare edge case. The existing n1_new/n2_new > inn_dim1 guard a few
lines later (added in an earlier pass) only rejects the *result* after
this write already happened -- it could never have prevented the
out-of-bounds write itself. This is almost certainly why it went
undetected in this session's earlier (smaller-mesh) division sanity
checks: the same 8-byte overflow was very likely happening every time
too, just landing in heap padding that didn't matter until this larger
mesh's allocation pattern made it corrupt something that mattered.

FIX: sized inn_neighbor1_new/inn_neighbor2_new as inn_dim1+2 (matching
what the callee actually needs given inn_neighbor1/inn_neighbor2 are
passed whole), and pass them as full arrays (no slicing) at the call
site so the actual argument size matches the dummy's declared size
exactly. The downstream n1_new/n2_new > inn_dim1 guard is unchanged and
still does its job -- now safely, after a write that can no longer
overflow anything.

BUG: VideoWriter "Frame must be H by W" in Movie_Code.m /
Movie_Code_WithMyosin.m / MovieCode_halflatt.m

be 1280 by 1280" -- VideoWriter locks in its frame size from the FIRST
writeVideo call and then hard-errors on any later frame that comes back a
different pixel size. All three movie scripts captured frames via a bare

figure('Position',...) only sets a *nominal* size; the actual rendered

stop the window from being resized mid-loop, added `drawnow` right before
each getframe (avoids capturing a frame mid-layout), and -- the actual
guarantee, independent of *why* a frame might differ -- lock in the first
frame's [height width] and `imresize` any later frame that doesn't match
before handing it to writeVideo. MovieCode_halflatt.m didn't create its
own figure at all (relies on whatever gcf currently is); left that as-is
rather than changing its behavior, and just normalize the frame size
regardless of which figure produced it.

     allocate(mot(v_dim2)) does not guarantee zero-initialized memory --
     this was accumulating the hotspot contribution on top of whatever
     undefined bytes happened to already be there, "working" only by
     luck when that memory happened to already be zero.
  2. The accumulation loop visited each vertex once per INCIDENT CELL (do
     ic=1,Nc; do jc=1,num(ic)) and divided every contribution by a fixed
     3.0d0 -- correct ONLY for an interior vertex (shared by exactly 3
     cells: 3 visits x contribution/3 = contribution). A boundary vertex
     (shared by fewer than 3 cells) only got 1 or 2 visits, i.e. 1/3 or
     2/3 of the intended value -- an artificial dip in motility right at
     the tissue edge, purely a counting artifact.

FIX: zero mot at the top (matching Give_Motility_Gradient's convention),
and visit each unique vertex exactly once (a vertex_done flag) instead of
once per incident cell, computing its full contribution directly with no
fudge factor -- correct regardless of how many cells share a vertex.

VERIFICATION: recompiled; ran a fresh 24x24 scratch mesh with
if_motility_hotspot on (number_of_hotspot=2, one hotspot deliberately
centered on a tissue-edge cell so its own vertices are a mix of
boundary/interior). Before this fix, that cell's boundary vertices
(shared by 1 or 2 cells) would have gotten ~1/3 or ~2/3 of etas_max;
after the fix, ALL of that cell's vertices -- boundary and interior alike
-- correctly read ~0.040 (~etas_max), matching their equal physical
proximity to the hotspot center. min(mot)=0.0 (clean zero far from any
hotspot, confirming the zero-init fix) and max(mot)~0.0401 (two nearby
hotspots' contributions additively overlapping slightly, as expected).

NOTE for the user: the currently-running vertexmain.exe process (nrun=2,
already in progress) is still executing the OLD in-memory code from
before this recompile -- Fortran fixes never affect an already-running
process, only a fresh launch of the newly-built binary. Its existing
data/nrun2_motility_store.dat was written by the OLD (boundary-
suppressing) logic.

USER REPORT: at a late snapshot (it=200000) of a real production run
(gradient motility + division), expected more high-motility ("red")
cells near the bottom (as set by the gradient at the start) but observed
low-motility cells surrounding high-motility ones instead -- asked
whether this is expected or a bug.

DIAGNOSIS (confirmed against the real run's own nrun2_ data, not just
theory): mot is a per-VERTEX value assigned once, at it=1, from each
vertex's position AT THAT INSTANT (Give_Motility_Gradient, called only
before the main loop, vertexmain.f90) -- a vertex carries that value
wherever it physically moves for the rest of the run (a Lagrangian tag),
never recomputed from its current position. Measured
corr(cell-mean-mot, cell's CURRENT y) directly from the real run's
snapshots: -0.66 at it=20000, degraded to -0.31 by it=200000, with the
very bottom y-band actually LOWER mean motility than the band above it
by it=200000 -- a real inversion, not noise.

ROOT MECHANISM, isolated experimentally (scratch A/B pairs, 32x32 mesh,
same gradient parameters as production): with cell division OFF, the
gradient does NOT drift at all over 200000 steps (corr stays ~-0.97,
flat) -- active-force vertex diffusion alone is negligible at these
parameter values. With division ON (area_0=0.7, matching production),
Lagrangian-mode correlation measurably degrades (-0.7552 -> -0.7243 over
it=5000->80000) while an Eulerian-mode variant (see fix below) stays
flat (~-0.97, confirmed via a scratch-only debug dump of the TRUE
per-step mot array, byte-exact match to the analytic gradient formula at
every checked step, maxdiff=0.0). CONCLUSION: cell division -- not
passive vertex drift -- is the dominant real driver. Every division
creates new vertices whose motility must be estimated (even with the
split-edge interpolation fix earlier in this log); compounded over many
divisions, and diluted further by cell-level color averaging over
increasingly small/irregular post-division cells, this erodes the
visible gradient. This is NOT an arithmetic bug in the existing
Lagrangian implementation -- it is a mismatch between what the code
does (assign once, carry forever) and what the user's expectation
implies (an environmental/spatial field that stays anchored to
location).

FIX (per user request): new if_motility_Eulerian flag, read right after
if_motility_gradient in para_Simulation.dat (allocation.f90's read_input
-- inserted mid-file per explicit user request, NOT appended at the end;
this shifts every parameter read after it, so every existing
para_Simulation.dat needs the new line manually inserted at this exact
position -- done for the repo's own copy; ReadPara1Params.m's positional
`names` list updated to match). When if_motility_gradient is .true.:
if_motility_Eulerian=.false. (default, preserves all existing behavior)
keeps the current one-time Lagrangian assignment; =.true. instead calls
Give_Motility_Gradient again every step, right before
Motile_Force_Calculation (vertexmain.f90's main loop), re-deriving mot
from each vertex's CURRENT position -- so the gradient stays anchored to
physical location regardless of how much the tissue moves, mixes, or
divides.

OPTIMIZATION REQUIRED FOR THIS (Force.f90): Give_Motility_Gradient's old
implementation binned vertices into O(numver) y-"patches" purely to
decide which vertices to visit per pass, even though the assignment
formula only ever used the vertex's own continuous y (patch-independent)
-- equivalent to, but far more expensive than (O(numver * total
vertex-visits) vs O(total vertex-visits)), a single direct pass.
Replaced with the direct single-pass version. Verified byte-identical
to the old implementation first (scratch test_motgrad.f90 harness: 0
differing entries, maxdiff=0.0, on the same 3200-vertex/1024-cell mesh)
before relying on it being cheap enough to call every step.

BUG (requested fix): daughter cells' motility after division not properly
inherited from the mother cell (Proliferation.f90, Proliferation_Core)

User request: after a division, the new cells should carry the mother
cell's motility values.

CONTEXT: mot is a per-VERTEX (not per-cell) array (v_dim2-sized), set once
at startup -- uniformly (if_motility, mot=etas_max), or spatially via
Give_Motility_Gradient/Give_Motility_Hotspot. A division creates exactly
two brand-new vertices (maxinn+1 on the pair1(1)-pair1(2) split edge,
maxinn+2 on the pair2(1)-pair2(2) split edge -- see SplitPolygon/
Find_Bisector_Intersections); every other vertex in both daughter cells is
an already-existing mother-cell vertex that keeps its own mot value
unchanged by the split, so only these two new vertices ever need a value
assigned for the daughter cells to fully inherit the mother's motility.

ROOT CAUSE: the existing code (flagged in its own comment as "being
lazy") copied both new vertices' mot from mot(inn(1,ic)) -- a single
arbitrary vertex of daughter cell ic, unrelated to either actual split
edge. Harmless under plain uniform if_motility (every vertex equals
etas_max anyway), but silently wrong under if_motility_gradient/
if_motility_hotspot: both new vertices got the same borrowed value
regardless of where they actually sit, instead of each reflecting the
local field at its own position.

FIX: interpolate each new vertex from the mean of the two mother-cell
vertices whose edge it actually splits: mot(maxinn+1) =
0.5*(mot(idx_pair(1,1))+mot(idx_pair(1,2))), mot(maxinn+2) =
0.5*(mot(idx_pair(2,1))+mot(idx_pair(2,2))) (idx_pair was already an
existing argument to Proliferation_Core, unused for this purpose before).
Both daughter cells now stay consistent with the mother's local motility
field regardless of how it varies in space.

VERIFICATION: scratch copy (nrun=1, if_motility_gradient on, area_0
lowered to 0.35 to force immediate mass division on a 32x32 mesh), with a
temporary debug print comparing the new interpolated values against what
the old code would have assigned. Confirmed the new values track the
actual y-position-dependent gradient at each new vertex's real location
(e.g. two new vertices from the same division at vy~0.98 and vy~1.47
correctly got DIFFERENT mot, 0.037625 vs 0.036486, matching the gradient's
direction) while the old code would have assigned both the same borrowed
value (0.036757) regardless of their different positions. 256 divisions
sampled this way, all consistent. Confirmed via -fsyntax-only that the
real repo's Proliferation.f90 (fix applied, no debug prints) still
compiles cleanly.
